# Fixed Hash Function vs. Universal Hashing

Advanced Algorithms project comparing a deterministic fixed hash
(`h(k) = k mod m`) against a randomized Carter-Wegman universal hash,
on the *same* separate chaining hash table implementation, across
four input distributions.

**Research question:** does randomizing the hash function's
coefficients per table instance protect against the collision
patterns that a fixed modulus hash is structurally vulnerable to,
without materially hurting performance on "well behaved" inputs?

## Fixed hashing

`h(k) = k mod m` (`src/hash_functions.py::fixed_hash`). This is the
deterministic baseline: the same key always maps to the same bucket,
and the mapping is fully determined by `m`. That determinism is
exactly what makes it exploitable — anyone who knows `m` can construct
a set of keys that all collide (see [Dataset descriptions](#dataset-descriptions),
adversarial set).

## Universal hashing

Carter-Wegman universal hashing (`src/hash_functions.py::UniversalHash`):

```
h(k) = ((a*k + b) mod p) mod m
```

- `p` is prime and larger than the key range in use (defaults to the
  fixed Mersenne prime `2**61 - 1`, validated with a deterministic
  Miller Rabin test).
- `a` is drawn uniformly from `{1, ..., p-1}` (`a != 0`, since `a = 0`
  would collapse `h` to a constant function of `b` alone).
- `b` is drawn uniformly from `{0, ..., p-1}`.
- **Coefficients are drawn once, at instance construction — never per
  key.** A `UniversalHash` instance accepts an injected `random.Random`
  or `seed` so trials can be reproducible while still letting
  different instances draw independent `(a, b)` pairs.

Universal hashing gives a **probabilistic** guarantee, not a
zero-collision guarantee: for any two fixed, distinct keys, the
probability (over the random choice of `a, b` at construction time)
that they collide is at most `1/m`. A specific instance can still be
unlucky for a specific input; the guarantee is about the *expected*
behaviour over the random choice of the function, not about any one
draw being collision-free.

### Multi-hash family (k independent universal functions)

The universal method doesn't use a single hash function — it uses a
**family of `k` independently-parameterized `UniversalHash` instances**
(`src/hash_functions.py::make_universal_family(k, m, ...)`), all
mapping into the *same* `m`-bucket array. `k` is configurable
(`config.UNIVERSAL_K_VALUES`, typically 2-5); `k = 1` reproduces plain
single-function universal hashing exactly.

- **Insert:** picks **one** of the `k` functions uniformly at random
  (via the table's own placement RNG, independent of whichever RNG
  drew the functions' `(a, b)` coefficients) and stores the key in
  that function's bucket.
- **Search:** the key could have been placed by any of the `k`
  functions, so search computes the candidate bucket for **every**
  family member, **dedupes** the candidate bucket indices, and probes
  them in a deterministic order (first occurrence, following family
  order). This guarantees no false negatives: whichever member placed
  a key, its candidate bucket is always among those probed.
- **Search-cost model:** probing is **short-circuit-on-find** — as
  soon as the key turns up in a probed bucket, search stops and
  returns. A miss is the expensive case: every probed candidate bucket
  is scanned in full, and every comparison made along the way is
  counted. (Alternative considered and rejected: always probe all `k`
  candidate buckets even on a hit, which would make hit cost equal to
  miss cost — rejected because it charges successful lookups for work
  a real implementation wouldn't need to do.)
- **Shared `m`-bucket array:** all `k` functions map into the same
  array used by the fixed-hash table, so `m` and the load factor are
  identical between methods — this is what keeps the comparison fair.
  Chain-length and collision metrics are computed on that same array,
  unchanged.
- **`k = 1` special case:** with one family member, "pick one at
  random" is trivial (there's nothing else to pick) and "probe all
  deduped" probes exactly the one bucket a single hash function would
  have — so a `k=1` universal table is byte-for-byte identical in
  behaviour to a plain single-`UniversalHash` table.

This is still a **probabilistic** scheme, not a zero-collision
guarantee — a family of `k` functions reduces the chance that an
adversarial key set concentrates into one bucket under *every* member
simultaneously, but it doesn't eliminate collisions.

## Hash table architecture

`src/hash_table.py::HashTable` uses **separate chaining**: `m`
buckets, each a plain Python `list`. The hash strategy is
**dependency-injected as a family** — `HashTable(size=m,
hash_family=[...])` — so the exact same data structure and code path
is used for both fixed and universal hashing; only the injected family
differs.

- **Fixed hashing → family of length 1**: `make_fixed_family(m)`
  returns `[make_fixed_hash(m)]`. With one member, insert's "choose
  one at random" and search's "probe all deduped" both degenerate to
  the single fixed bucket, reproducing the original single-hash
  behaviour exactly.
- **Universal hashing → family of length `k`**: `make_universal_family(k,
  m, ...)` returns `k` independently-parameterized `UniversalHash`
  instances sharing one `m`-array.
- Every family member is a single-argument callable `f(key) -> int`
  (`make_fixed_hash(m)` adapts `fixed_hash(key, m)` via
  `functools.partial`; `UniversalHash` instances are already callable
  as `h(key)`).
- A `HashTable` instance owns its own **placement RNG** (`seed=`/`rng=`
  constructor args), used only to choose which family member places a
  new key on insert. It is seeded independently of whatever RNG drew
  the family members' `(a, b)` coefficients, so "which function placed
  this key" is reproducible per table instance without entangling it
  with coefficient generation.

**Duplicate policy:** the table behaves like a *set* of keys.
Re-inserting a key already present in *any* of its candidate buckets
(across all `k` family members) is a no-op — it does not create a
second entry and does not raise. This policy is applied identically
regardless of which hash strategy is injected, so duplicate handling
never differs between the two methods being compared. See [Design
decisions](#design-decisions).

**Search instrumentation:** `search()` counts every key comparison
made while scanning each probed bucket, short-circuiting as soon as
the key is found. Finding the key on the k-th comparison (within
whichever bucket it's found in, considering buckets in probe order)
costs `k` comparisons; a full miss scans and counts every element in
every probed candidate bucket. The running total is
`comparison_count`, resettable via `reset_counters()`.

## Dataset descriptions

All four generators live in `src/datasets.py`, are seedable where
randomness is involved, and run in O(n) time.

1. **Uniform** (`uniform_dataset`): `n` random integers drawn from
   `[1, 10n]`. The "generic" workload — no structure for either hash
   to exploit or be defeated by.
2. **Sorted** (`sorted_dataset`): exactly `1, 2, ..., n`. Tests
   behaviour on already-ordered, densely-packed key sequences.
3. **Adversarial** (`adversarial_dataset`, requires `m`): `k_i = i *
   m` for `i = 1..n`. Under the fixed hash, `i*m mod m == 0` for
   every `i`, so **every key maps to bucket 0** — this is the
   textbook worst case for `h(k) = k mod m`, and it is constructible
   by anyone who knows `m`. A universal hash's `(a, b)` are chosen
   independently of this construction, so it is very unlikely to
   concentrate these same keys into one bucket.
4. **Near-duplicate** (`near_duplicate_dataset`): `n` keys drawn (with
   heavy repetition) from a pool of size `max(1, n // 10)`, so each
   pool value repeats roughly 10 times on average. Still yields
   exactly `n` keys. Exercises the set-based duplicate policy under
   load.

## Metrics

`src/metrics.py::compute_chain_stats` computes, from a populated
`HashTable`:

- `max_chain_length` — longest chain.
- `average_chain_length` — mean chain length across all buckets
  (equals `unique_keys / size`, the achieved load factor).
- `non_empty_buckets` / `empty_buckets`.
- `chain_length_stdev` — population standard deviation of chain
  lengths.
- `collision_count` — inserted unique keys beyond the first in each
  bucket, summed over all buckets (a bucket with `k` unique keys
  contributes `max(k - 1, 0)`).

`src/metrics.py::validate_adversarial_concentration(n, m)` is a
sanity-check helper: it builds a fixed-hash table over the
adversarial dataset, asserts every unique key landed in bucket 0, and
returns the measured max chain length. `run_experiments.py` calls it
as a pre-flight check before every run (see [How to run
experiments](#how-to-run-experiments)).

Timing and cross-trial statistical aggregation aren't in this module —
that's `src/experiment.py` and `src/statistics.py`, described below.

## Complexity note

Under the standard "simple uniform hashing" assumption (each key
equally likely to land in any bucket, independent of other keys),
separate chaining gives expected `O(1 + alpha)` insert/search, where
`alpha = n/m` is the load factor. The worst case is `O(n)`, reached
when every key lands in the same bucket, degenerating search into a
linear scan of a single chain.

The adversarial dataset triggers exactly that worst case **for fixed
hashing**, because `k_i = i*m` is constructed specifically so that
`k_i mod m == 0` for every key — the simple uniform hashing
assumption fails completely, since the mapping is deterministic and
known. Universal hashing makes this worst case unlikely (not
impossible) for the *same* key set: its coefficients `(a, b)` are
chosen independently of how the keys were constructed, so the
Carter-Wegman guarantee (collision probability `<= 1/m` per pair,
in expectation over the random choice of the function) still applies
to this input.

## How to run experiments

```bash
python run_experiments.py                # full run: config.py's defaults
python run_experiments.py --quick         # tiny end-to-end pipeline check
python run_experiments.py --n-values 1000 5000 10000
python run_experiments.py --trials 30
python run_experiments.py --seed 42
python run_experiments.py --distributions uniform sorted adversarial near_duplicate
python run_experiments.py --k 1 2 3 5     # universal family sizes to test
```

Every run first executes an **adversarial sanity check**
(`run_adversarial_sanity_check` in `run_experiments.py`): it builds a
fixed-hash table over the adversarial dataset and asserts every key
concentrated into bucket 0 (via
`validate_adversarial_concentration`), then builds a universal-hash
table (family size = the largest requested `k`) over the *same*
dataset and asserts its max chain length is smaller. The run aborts
loudly (an `AssertionError`) if either check fails, before any trials
run.

For each `(n, load_factor, distribution, k)` combination it runs
`--trials` independent trials (`src/experiment.py::run_single_trial`):
one dataset per trial, fed into both a fixed-hash table (hash family
of size 1) and a universal-hash table (hash family of size `k`), with
the same `n // 2` search-key sample used against both. Progress is
printed per configuration, not per insert/search.

## Reproducibility

`config.py` defines `BASE_SEED = 42` as the project-wide seeding
convention, intended to derive per-trial seeds (e.g.
`BASE_SEED + trial_index`) once the experiment runner exists.

- `uniform_dataset(n, seed=...)` and `near_duplicate_dataset(n,
  seed=...)` accept an explicit seed and are fully deterministic for
  a given seed.
- `sorted_dataset(n)` and `adversarial_dataset(n, m)` are inherently
  deterministic (no randomness involved).
- `UniversalHash(m, ..., seed=...)` (or an injected `rng`) makes the
  one-time `(a, b)` draw reproducible, while still allowing separate
  instances to draw independently by using separate seeds or a
  shared, sequentially-advancing `random.Random`.
- `make_universal_family(k, m, seed=...)` threads one `random.Random`
  through the construction of all `k` members, so the whole family's
  coefficients are reproducible from a single seed while each member
  still draws independently. `HashTable(..., seed=...)` seeds the
  table's own placement RNG separately, so which member placed a given
  key is *also* reproducible, without being entangled with coefficient
  generation.

## Design decisions

Places where more than one reasonable implementation choice existed,
and which one I went with (full list with reasoning in
`DECISIONS.md`):

- **Duplicate policy is set-based**: re-inserting an existing key is a
  no-op, applied identically for both hash strategies.
- **`collision_count` = unique keys beyond the first, per bucket,
  summed**: the standard chaining-collision definition, hand-verified
  in `tests/test_metrics.py`.
- **Search comparisons include the matching element**: a hit on the
  k-th element costs `k` comparisons, matching the standard `O(1 +
  alpha)` analysis.
- **Universal hash `p` defaults to `2**61 - 1`**, validated via
  deterministic Miller-Rabin, comfortably larger than any key range
  the datasets here produce.
- **`UniversalHash` accepts optional explicit `a`/`b`** (validated) so
  invalid-parameter cases like `a = 0` can be exercised directly in
  tests, since normal random draws never produce `a = 0`.
- **Universal hashing is a family of `k` independent functions
  sharing one `m`-array**, not a single function: insert picks one
  member at random per key, search probes all members' candidate
  buckets (deduped, short-circuit-on-find). `k = 1` is a special case
  that reproduces plain single-function universal hashing exactly.
